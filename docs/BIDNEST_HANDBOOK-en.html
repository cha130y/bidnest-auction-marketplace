Chapter 01What this system is

BidNest is a marketplace that combines two ways of reaching a price in one system — real-time auctions and a buy-now shop — sharing the same user accounts, cart, payment and shipping

One user can be both a buyer and a seller on a single account, with no separate shop sign-up, and whether an item comes from an auction or from the shop, it all ends up in the same place: order → payment → shipping → delivered

Where the two paths meet

The auction path

Seller creates a draft → publishes → the system opens it on schedule → people bid against each other → the system closes it on schedule → a winner → the winner pays at the checkout page

The shop path

Seller lists a product with stock and price → buyer adds it to the cart → pays at the same checkout page

The meeting point is a single POST /orders/checkout, which accepts cart items, a won auction lot and a price successfully negotiated with the AI, and writes them as orders in the same format — which is why the order_items table has both a product_id and an auction_id column, with only one of them set at a time

V1 scope (very important when answering questions)

Where the story ends

V1 ends when the auction closes and the item is shipped — there are no refunds or cancellations after payment yet. SOLD and UNSOLD are true end states and never go back, and payment is simulated, not yet connected to a real payment gateway (paying a total of exactly 666.00 is always declined, for testing the FAILED path)

Chapter 05How the features connect

This chapter is the heart of the document — it answers what the screen you see calls, what the server does next, and which table the data lands in. After reading it you'll be able to walk through the path of a feature you didn't build

The web side and the server side connect through 4 channels

1 · REST through a single apiFetch

Every API call from the web app goes through one place, apps/web/src/lib/api/client.ts. It attaches the bearer token, turns NestJS errors into messages the UI can show, and sets cache: "no-store", because nothing in this API can be cached by URL

2 · session cookie ↔ bearer token

NextAuth holds the browser session (an httpOnly cookie), while apps/api owns the real tokens. Tokens are never stored in localStorage · when the access token expires, apiFetch reads the session again and retries once

3 · Socket.IO 2 namespace

/auctions = auction rooms, publicly readable, no token needed · /user = each person's private channel, which requires authentication at connection time or is cut off immediately

4 · A single Prisma schema

apps/api/prisma/schema.prisma is the single source of truth for the data structure. Every module reads and writes through Prisma · Dev 2 owns the schema and migrations; don't change them without asking

The most common point of confusion for newcomers

The apps/web/src/app/api/ folder is not the system's API — it's Next.js route handlers that exist only to handle cookies (exchanging tokens with LINE, storing the OAuth pending token, storing the trusted-device token). All the business rules always live in apps/api on port 4000

How to read the tables in this chapter

Each row is one path, read from left to right as which screen → which endpoint it calls → which table the data lands in. Paths nobody clicks, which the system runs on its own, are marked system-driven

Three rules you have to explain correctly

RuleWhat the code actually does

BID-001		 The first bid must be ≥ the starting price · from the second bid on, it must be ≥ the current price + the bid increment

How real-time works

The browser joins the auction:<id> room through the /auctions namespace. The server broadcasts 6 events into that room, and the web side (use-auction-room.ts) doesn't paste the payload onto the screen directly, but calls GET /arena to re-read the whole set, because the price, leader, next minimum bid, closing time and extension quota must all stay consistent together

eventWhen it happens
auction:bidSomeone placed a bid successfully
auction:extensionAnti-sniping pushed the close out
auction:presenceSomeone joined/left the room
auction:startedThe timer opened the auction
auction:endedThe timer closed it and decided the result
auction:cancelledThe seller or an admin cancelled it
Why the auction room socket doesn't need login

Because published auctions are already public data (AUC-005), and this room sends the same data as the public GET. You can send a token too, but it doesn't change what you see — it only lets the system know who closed their tab, so the viewer count stays accurate. Bidding still goes through HTTP and the guard as usual; the socket doesn't accept bids

What actually happens when you click pay

  1. Every price is recomputed on the server — not a single number sent from the browser is trusted
  2. Checks the items are still on sale and stock is sufficient — if not, it responds with an error code (ITEMS_UNAVAILABLE) before charging
  3. Calls the simulated payment provider — a total of exactly 666.00 is always declined (PAYMENT_DECLINED)
  4. Deducts stock conditionally on stockQty >= quantity — if two people pay at once, the loser rolls back entirely, so stock can't be oversold
  5. Writes orders split by seller + creates shipments + removes the items from the cart
  6. Notifies the buyer and every seller in that round (NOT-005) and pushes it over the /user socket

A won auction lot takes exactly the same path; the only difference is that the price comes from the soldPrice the system wrote when the auction closed, and the right to pay comes from winnerUserId — there's no field in the request a buyer could use to change the price, and order_items.auction_id is unique, so the same lot can't be paid for twice

A detail that is often explained wrong

OUTBID goes only to the person who was just overtaken, not to everyone who has ever bid — people further down were already overtaken in earlier rounds, and re-alerting them every time the price moves would make the bell useless. Bidding over your own bid doesn't count as overtaking anyone · the notification row is written in the same transaction as the bid row, so a recorded bid always has its notification alongside it

How a negotiation is decided

The seller sets an acceptable floor price, which the buyer never sees — the comparison happens only on the server — and it responds with one of 3 outcomes:

  • ACCEPTED — the offer is ≥ the listed price or ≥ the price the system countered with in the previous round
  • COUNTERED — the offer is between the floor and the listed price; the system counters at the average of the two
  • REJECTED — the offer is below the floor, or asks for more than the stock

The bold condition in the first item is what lets a negotiation end — a counter is the average of the offer and the sticker price, so it's always below the sticker price. Without counting its own counter, offering exactly the counter would just get a new counter, round after round, getting closer to the sticker price but never reaching it · accepting a counter is not subject to the 5-minute cooldown, because that number came from the server itself, so sending it back reveals nothing about the floor · the floor check still sits above every rule

What happens after a successful negotiation

ACCEPTED unlocks that price for 15 minutes, usable once, tied to the buyer, the product and the quantity offered — but checkout still has to be completed; a successful negotiation is not a successful purchase

During those 15 minutes, GET /offers/pending returns the offers that can still be paid (with a token re-signed on every read), and PayableOffersBanner shows them on the product page, cart, checkout and order list — you can leave the page and come back to pay without negotiating again · the filter is a single line, expiresAt > now, because using the token pushes expiresAt into the past, so one condition excludes both “expired” and “already paid” at once

When the support chat hands over to an admin

The AI answers from a prepared question bank (faq-knowledge-base.ts). When it can't answer, or the user asks to talk to a person, the session is escalated and shows up in the admin inbox immediately via the support:inbox_updated socket — every online admin is in this shared room from the moment they connect, without opening any page first

Two full paths — for explaining to others

Path 1 · auction all the way to receiving the item

  1. Seller creates a draft

    /sell → POST /auctions/drafts → a new row in auctions with status DRAFT · images are uploaded via POST /uploads/images to Cloudinary, and the URLs are stored in auction_images

  2. Completeness check, then publish

    GET /auctions/drafts/:id/validation says what's still missing · click publish → POST /auctions/drafts/:id/publish → status becomes SCHEDULED

  3. The system opens the auction nobody clicks

    The timer sees the start time has come → changes it to ACTIVE → broadcasts auction:started to the room

  4. People join the room and bid

    /auctions/[id] connects the socket to the auction:<id> room · click bid → POST /auctions/:id/bids → everything is checked and written in a single transaction → broadcasts auction:bid → every screen in the room calls GET /arena to re-read the whole state · the person who was overtaken gets an OUTBID notification

  5. The system closes and decides nobody clicks

    Time runs out (including time added by anti-sniping) → the timer changes it to SOLD or UNSOLD depending on whether the reserve was met → writes soldPrice and winnerUserId → broadcasts auction:ended → notifies the winner and the seller

  6. The winner pays

    GET /auctions/won says which lots are waiting for payment → the /checkout page → POST /orders/checkout → the order + shipment are created exactly like a shop purchase

  7. The seller ships

    /sell/orders/[id] → PATCH /orders/:id/shipment, one status at a time PROCESSING → SHIPPED → IN_TRANSIT → DELIVERED Each time writes shipment_events + notifies the buyer + pushes order:status_changed

Path 2 · buy now from the shop

  1. Seller lists a product

    /sell/products/new → POST /products → products + product_images, with stock and price

  2. Buyer finds it and adds it to the cart

    /shop → GET /products (search + category filter) → POST /cart/items · one cart can hold items from several shops

  3. Wants it cheaper — makes an offer for the AI to decide

    POST /products/:id/offers → answers ACCEPTED / COUNTERED / REJECTED by comparing against the seller's floor price · after a COUNTER, “Accept this price” can be clicked right away, with no cooldown

  4. Payment

    Cart items: /checkout → POST /orders/checkout → every price recomputed → stock deducted → split into per-seller orders → cart cleared → everyone notified

    A negotiated price: /checkout?offer=<offerId> → the screen reads the offer from GET /offers/pending and sends offerAcceptToken with checkout → the unit price comes from that offer, without also applying the quantity discount (PROD-007, they don't stack)

  5. Tracking until it arrives

    The buyer watches at /orders/[id] · the seller updates at /sell/orders/[id] — the same path as step 7 of the auction path

Chapter 06Testing

This chapter covers two things decided at different moments — choosing the right tool is decided when you are about to write a new test file, while running every layer is decided when you are about to submit work

Which tool — decided by two questions

This project has 4 testing tools, and they don't compete — each one has its own place. When writing a new test file, ask these two questions in order and the answer falls out, with no need to argue about preferences

Question 1 · which app is the file in → gives you the runner

In apps/web = Vitest · in apps/api = Jest — this isn't a matter of taste; each app already has its own config, and picking the wrong one = the file never runs

Question 2 · what are you testing → gives you the library on top

A plain function = nothing extra needed · a component the user clicks or types into = RTL · a real endpoint over HTTP = Supertest

A common misunderstanding

RTL is not an alternative to Vitest, and Supertest is not an alternative to Jest — both are used together with a runner, not instead of one · put simply: the runner is what starts the tests and says whether they pass or fail, while RTL and Supertest are the tools used to reach in and touch the thing being tested

What to testRunnerlibraryWhere the file goes
Plain web-side functions — price formatting, time-remaining calculations, list filtering Vitest — apps/web/src/lib/<name>.test.ts
Components the user clicks, types into, or sees text change in Vitest RTL apps/web/src/components/<module>/<name>.test.tsx
Server-side rules — services, mappers, utils that don't touch the real database Jest — (mock Prisma) apps/api/src/<module>/<name>.spec.ts
Real endpoints, called over HTTP against the real database Jest Supertest apps/api/test/<name>.e2e-spec.ts

Why the two apps use different runners

apps/api → Jest

It came with nest new on scaffold day, and e2e uses NestJS's Test.createTestingModule(), which is tied to Nest's DI system — moving to another runner would mean rebuilding how modules are assembled from scratch for nothing in return

apps/web → Vitest

Next.js 16 is pure ESM and uses the @/* alias · Vitest reads paths from tsconfig.json itself via resolve.tsconfigPaths — so a path that resolves in the editor also resolves in tests without declaring it again in the config file

Don't swap them

Don't drag Vitest into apps/api or Jest into apps/web just because you prefer one — one app with two runners means whoever opens a file can't tell what it runs with, and pnpm test at the root would silently fail to run everything

RTL — test what the user sees, not what the code does inside

  • Find elements by what users find them by — getByRole("button", { name: "Bid" }) or getByLabelText, not a class or test id · if it can't be found by role, that usually means people using a screen reader can't find it either — that's a real bug, not a test problem
  • Use user-event, not fireEvent — user-event simulates the sequence a real browser goes through (focus → keydown → input → change), while fireEvent fires a single event, which can pass even when the real thing is broken
  • No need to call cleanup yourself — apps/web/src/test/setup.ts already sets afterEach(cleanup); without it, components from the previous test would linger in the DOM and getByRole would find two and throw

Supertest — hit an app assembled the same way as production

The line that makes tests lie if you forget it

Every e2e file must call configureApp(app) after createTestingModule — ValidationPipe and the exception filter are installed in main.ts, not in AppModule. A file that forgets this line runs an app with no input validation at all: the tests are nicely green while the real thing accepts anything

What doesn't need tests

A test that protects nothing has a real cost, because it has to be fixed every time the code moves · these three can be let go: constants and types (typecheck already catches them) · whether Prisma works (that's testing their library, not our code) · components that render fixed text unconditionally · the best value is wherever there are conditions or calculations — minimum bids, anti-sniping decisions, stock deduction

Which approach — at which layer a test pays off

Once the tool is right, there is a more important question left: at which layer should this be tested · one principle is enough — test at the lowest layer that can still genuinely prove what you are worried about

To apply it, ask yourself "if this breaks, where does it break" and test there — not climbing to the top layer because it feels more real. Upper layers are much slower and break more often for reasons unrelated to our code

What you fear will breakTest at layerWhy other layers can't catch it
Wrong calculations — minimum bid, quantity discount, time remaining, the AI counter average unit e2e catches it too, but far more slowly, and when it goes red it won't tell you which line is wrong
A button enabled/disabled at the wrong time · an error message not showing · the screen not responding to input component (RTL) typecheck and next build only catch whether it renders, not what happens when you click
A migration fails to apply · a unique index collision · two people clicking at once driving stock negative · guards wired in the wrong order e2e only unit tests can't catch these at all, because Prisma is mocked away — these are behaviors of the real database
A page that breaks at build time · a Server Component calling something it can't no test needed next build in CI already catches it — a duplicate test is paying for nothing
Paths spanning several pages — auction ends → go to checkout → get an order still manual e2e only covers the API side · this project has no tests driving a real browser yet
Rule against test bloat

Don't test the same rule at two layers — if the minimum-bid calculation is tested at the unit level, e2e should only test that it is wired correctly (hitting the real endpoint returns 400 with the right error code), not re-test every case of the formula · e2e takes about 75 seconds per file, while unit tests finish in a few seconds — duplicated tests don't add confidence, they add waiting time for everyone on every PR

When writing a test pays off most

Right after finding a bug — write a test that is red because of that bug first, then fix the code until it is green, because that is the only moment you know for sure the test catches the real thing · if you write it after the fix, you'll never know whether it was ever really red · an example in this project is the commit fix(BID-001), which came with its own test in the same change

WebSocket — why auctions need it

The question to answer first is where REST alone falls short · the answer lies in the nature of the data: auction prices change because of other people, not the person watching — REST can only answer when someone asks, and someone watching an auction has no way of knowing when to ask

OptionWhat you actually get
Manual refresh The user has to guess when the price moved — in the last minute of an auction room it is simply unusable
Polling every 1–2 s 1 viewer = dozens of empty requests per minute, and still slower, because news arrives up to one polling cycle late — paying more to get something worse
WebSocket The server speaks when something actually happens, with no empty requests, and it arrives immediately

The deciding criterion is whether the data is pushed by events the viewer didn't cause — auctions, notifications and chat meet it · the cart and the profile page don't, because they only change when their owner acts, so sockets were not bolted onto every page

Why Socket.IO rather than raw WebSocket

These 4 things are needed anyway; with raw WS you would have to write them all yourself

Rooms

Events must go only to people watching that auction, not everyone connected · raw WS needs its own connection registry

Automatic reconnection

A network hiccup mid-auction is the worst possible moment · use-auction-room.ts sets a backoff of 1 s → up to 10 s

namespace

Separates the public channel from the private one without opening extra ports or doing a handshake yourself

fallback

Networks that block WebSocket fall back to long-polling on their own, without our code needing to know

Plus, NestJS has @nestjs/platform-socket.io built in — a gateway is written as a class using the same DI as any other service, with the same access to PrismaService, no manual wiring needed

Why there are 2 namespaces

Because the two channels have opposite security properties — combining them would mean filtering per person inside one room, where a single mistake leaks data

/auctions/user
Who can join no token needed authenticate at connection
Why Published auctions are public data (AUC-005), and the room sends the same data the public GET already sends — there is nothing to authorize Every event is addressed to a single account, so a socket that can't authenticate has no reason to stay connected
Can a token be sent? Yes, and it doesn't change what you see — it lets the system know who closed their tab, so the viewer count is right (LIV-001) Required
A deliberate detail

/user authenticates at connection time, not when the join message is sent — so there's never a moment when an unidentified socket sits on this namespace waiting to say who it is

The most important principle — the socket says "something changed", not "what it changed to"

Every handler in use-auction-room.ts calls the same onChange(), and the screen then calls GET /arena to re-read the whole set — nowhere is an event's payload pasted onto the screen directly

The reason: the arena is a set of values that must be consistent as a whole — current price, leader, next minimum bid, closing time and remaining extension quota · the API computes them together, and patching them in field by field is how a screen ends up offering a bid the endpoint will reject · the cost is 1 request per event, and what you get back is a state that is always correct as a whole

The socket doesn't take commands

Bidding still goes through HTTP and the guard as usual — the socket only accepts the room-join message; everything else is one-way (outbound only). The result is that no business rule has to be written in two places. If bids were also accepted over the socket, every rule (minimum bid, duplicate-bid protection, user permissions) would need a second copy, and two copies inevitably drift apart one day

Presence is kept in memory on purpose

presence-registry.ts keeps which socket belongs to whom and which auction it is watching, purely in memory. The reason is that it describes who is connected to this process — when the process dies, the sockets it held go with it, so the data is naturally correct, with no one needing to clean it up

And it counts rather than flags, because one person can open the same auction in two tabs — closing one tab doesn't mean leaving the room

A limitation to know before scaling out

Both presence and broadcasting are tied to a single process · the day apps/api runs as more than 1 instance, a Socket.IO adapter (e.g. Redis) has to be added first, otherwise people connected to different instances won't see each other's events, and the viewer count will only include people who happen to be on the same instance · there is no adapter in the code yet (searching all of apps/api/src finds neither Redis nor IoAdapter) — it is designed for a single instance, and this is the first thing to fix before adding instances. The actual replica count is set in Railway's dashboard, not in the repo, so check there before concluding how many are running

Docker — why it is needed and what it really gives you

This project uses Docker in two completely different roles — tell them apart first, or you'll be confused about why our code is sometimes in a container and sometimes not

On a dev machineIn production
File infra/docker/compose.dev.yml Dockerfile + docker-entrypoint.sh
What's in the container The surroundings — Postgres + Maildev The app itself — apps/api
Where our code is Runs directly on the machine with pnpm dev — edit a file and see the result immediately Built into the image

Role 1 · compose.dev.yml — making 5 machines identical

Without it, everyone installs Postgres themselves and ends up on different versions — "works on my machine, not on yours" is the most expensive cost for a 5-person team with 14 days · every line in the compose file has a reason

SettingWhat problem it solves
postgres:17Everyone gets exactly the same version, matching what Railway uses — bugs caused by SQL version differences show up locally
127.0.0.1:5433:54325433 deliberately avoids clashing with a Postgres some people already have installed · bound to 127.0.0.1, so the dev database never shows up on the LAN
maildevLogin in this system requires an emailed OTP on every entry path — without a local mail catcher, login can't be tested at all, and nobody has to share real SMTP credentials
pg_data volumeData survives even if the container is deleted — no need to seed again every morning
healthcheck: pg_isreadySays the database is actually ready for queries, not just that the container is up — so scripts can wait for the right moment
restart: unless-stoppedComes up by itself when you start the machine, no need to start it every day
Why apps/web and apps/api aren't in compose too

Because it would cost something dev needs every minute — hot reload · mounting source into a container on Windows makes the watcher noticeably slower, in exchange for a sameness our code doesn't need, since it already runs on Node 24 identically on every machine · so Docker wraps only the things that are hard to install and version-sensitive

Role 2 · Dockerfile — so the deploy target doesn't need to know about the monorepo

Railway doesn't need to know what a pnpm workspace is, or that packages/contracts exists — it gets a single runnable image · the trade-off is that the Dockerfile has to know these things instead, and every line in it has a reason

What was doneWhat happens without it
build context = the repo rootpnpm-lock.yaml and pnpm-workspace.yaml live at the root — this is why Railway's Root Directory field must be left empty, not set to apps/api
multi-stage deps → build → runtimeThe deps stage copies only the manifest files first — editing source files doesn't reinstall everything
Debian, not AlpineThe Prisma schema engine is a glibc binary · on musl it needs a different build and breaks at deploy time, the worst possible moment

Copy all of node_modules, no pruneThe Prisma CLI is a devDependency, but the entrypoint needs it — a few hundred MB of space traded for a container that migrates itself, making a redeploy a single step
node:24 as the baseThis version is what production actually runs · CI and the docs have been aligned with it — previously CI tested on 22 even though no environment ran 22 at all, meaning code passed CI without ever being proven on the version really in use · now this number is declared in one place, engines.node, which Vercel also reads to pick the runtime for apps/web, so both platforms are controlled from the repo
USER nodeNothing in this image needs root

The entrypoint does two things, and both matter

  1. prisma migrate deploy before start

    The database a freshly started container meets is often several migrations behind the code — that is the normal state after a deploy · migrate deploy applies only what's missing, never rewrites history, and takes an advisory lock first, so two containers starting at the same time can't fight over the same migration

  2. exec node, not a plain call

    exec makes the app replace the shell and become PID 1 — receiving SIGTERM from the platform directly · without it, the shell swallows the signal, graceful shutdown never runs, and the container gets killed while requests are still in flight

Why apps/web doesn't go into Docker

Vercel builds straight from source and expects the standard Next.js layout · putting it in a container would lose the automatic preview deploys, image optimization and edge network that come for free — wrap things to make them identical, but don't wrap what the platform already does better

The criteria behind all three decisions

Choose what solves a real problem

WebSocket came in because polling is more expensive and slower, not because real-time sounds good — pages whose data changes only when their owner acts are still pure REST

Wrap only what's hard to install

Docker wraps Postgres and Maildev on dev machines but not our code, because that would lose hot reload for nothing in return

Give the truth a single home

Bidding rules live only behind HTTP, so the socket doesn't accept bids · the data structure lives only in schema.prisma

Know when your choice will break

In-memory presence is right for a single instance, and we wrote down clearly that an adapter is needed the day there is more than one

Releasing, step by step

  1. Check what's waiting to be released

    Read-only, doesn't create a PR, run it as often as you like
    git fetch origin
git log --merges --pretty='- %s' origin/main..origin/dev

    Nothing shows up = main has caught up with dev; nothing to release this time

  2. Open the release PR — the base must be main

    Open the compare page main...dev, check the top of the page says base: main ← compare: dev and shows Able to merge · use the title format chore: release dev to main - <short summary> · a short 2–3 line description citing the child PR numbers is enough (just type #153 and GitHub links it)

    This is the only kind of PR that may have main as its base; feature branches always go into dev

  3. Click Update branch right away, don't wait for CI

    Waiting for CI to finish before clicking Update wastes a whole round, because the commit being tested isn't the commit that will actually be merged · never choose Update with rebase, because it rewrites the whole history of dev

  4. Wait for all 3 CI checks to go green, then get 1 approval

    Branch protection requires lint-and-test + docker-build + e2e and 1 approval — you can't merge on your own

  5. Click Merge, and Railway and Vercel deploy on their own automatic

    docker-entrypoint.sh runs prisma migrate deploy itself before every start, so deploys don't need a separate migration step

  6. Check production is still breathing

    Git Bash — replace <railway-domain> with the real domain
    curl https://<railway-domain>/health
    PowerShell — curl here is an alias of Invoke-WebRequest, not the real curl
    Invoke-RestMethod https://<railway-domain>/health

    You must get {"status":"ok"} exactly like this, and nothing else — anything else means you hit the wrong server, because Railway domains are public names anyone can claim, and hitting the wrong one can also return 200. Finish by trying out at least 1 of the newly released features on the live site

Traps that break things silently

Putting quotes in the dashboard

.env can have quotes because dotenv strips them, but Railway doesn't — a value entered as "a@x.com" becomes an email with the quotes attached. This applies to every variable, not just ADMIN_EMAILS

NEXT_PUBLIC_* is baked in at build time

After setting it in Vercel, you have to click Redeploy for the Google button to appear — it is not read at runtime

OTP email can't be sent = nobody can log in

Users only see Internal server error · the real cause is in Railway's Deploy Logs; search for Failed to deliver

Releasing a migration mixed with ordinary features

Migrations are the hardest thing to roll back; a round that touches schema.prisma should be released on its own, so you immediately know what caused any breakage
