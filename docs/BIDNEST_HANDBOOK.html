บทที่ 01ระบบนี้คืออะไร

BidNest คือแพลตฟอร์มซื้อขายที่รวม สองวิธีหาราคา ไว้ในระบบเดียว — ประมูลแบบเรียลไทม์ กับ ร้านค้าซื้อทันที — โดยใช้บัญชีผู้ใช้ ตะกร้า การชำระเงิน และการจัดส่งชุดเดียวกัน

ผู้ใช้หนึ่งคนเป็นได้ทั้งผู้ซื้อและผู้ขายในบัญชีเดียว ไม่มีการสมัครแยกร้าน และไม่ว่าของชิ้นนั้นจะมาจากการประมูลหรือจากร้านค้า ปลายทางเดียวกันหมด คือ ออเดอร์ → จ่ายเงิน → จัดส่ง → ได้รับของ

สองเส้นทางบรรจบกันตรงไหน

เส้นทางประมูล

ผู้ขายสร้างร่าง → เผยแพร่ → ระบบเปิดตามเวลา → คนบิดแข่งกัน → ระบบปิดตามเวลา → ได้ผู้ชนะ → ผู้ชนะไปจ่ายเงินที่หน้า checkout

เส้นทางร้านค้า

ผู้ขายลงสินค้าพร้อมสต็อกและราคา → ผู้ซื้อหยิบใส่ตะกร้า → ไปจ่ายเงินที่หน้า checkout เดียวกัน

จุดบรรจบคือ POST /orders/checkout ตัวเดียว ที่รับได้ทั้งของในตะกร้า ล็อตที่ชนะประมูล และราคาที่ต่อรองกับ AI สำเร็จ แล้วเขียนเป็นออเดอร์ในรูปแบบเดียวกัน — นี่คือเหตุผลที่ตาราง order_items มีทั้งคอลัมน์ product_id และ auction_id โดยมีค่าได้ทีละอันเท่านั้น

ขอบเขต V1 (สำคัญมากเวลาตอบคำถาม)

เรื่องราวจบตรงไหน

V1 จบที่ ประมูลปิดและของถูกส่ง — ยังไม่มีการคืนเงินหรือยกเลิกหลังจ่ายเงินแล้ว สถานะ SOLD และ UNSOLD เป็นปลายทางจริง ไม่ย้อนกลับ และการชำระเงินเป็น การจำลอง ยังไม่ได้ต่อ payment gateway จริง (จ่ายยอด 666.00 พอดีจะถูกปฏิเสธเสมอ ไว้เทสทาง FAILED)

บทที่ 04ทำงานประจำวัน

เริ่มงานทุกครั้ง

terminal
git switch dev && git pull
git switch feat/auction-dev4   # เปลี่ยนเป็น branch ของตัวเอง
git merge dev
pnpm check
pnpm dev

ต้อง git merge dev ทุกวันเพราะ branch ของแต่ละคนแตกไว้ตั้งแต่วัน kickoff — ถ้าไม่ merge จะทำงานอยู่บนโค้ดเก่าและต่อของจริงที่คนอื่นทำไว้ไม่ได้เลย และต้อง pnpm check หลัง merge เพราะ merge ผ่านแปลว่าไม่มี conflict ระดับบรรทัดเท่านั้น ไม่ได้แปลว่าโค้ดยังทำงานถูก (CI รันเฉพาะตอนเปิด PR ไม่ได้รันให้ตอน merge ในเครื่อง)

pnpm install

บทที่ 05ฟีเจอร์ต่อกันยังไง

บทนี้คือหัวใจของเอกสาร — ตอบว่า หน้าจอที่เห็น เรียกอะไร เซิร์ฟเวอร์ ทำอะไรต่อ และ ข้อมูล ไปลงตารางไหน อ่านจบแล้วจะเล่าเส้นทางของฟีเจอร์ที่ตัวเองไม่ได้ทำได้

ฝั่งหน้าเว็บกับฝั่งเซิร์ฟเวอร์ต่อกันด้วย 4 ช่องทาง

1 · REST ผ่าน apiFetch ตัวเดียว

ทุกการเรียก API ของเว็บผ่าน apps/web/src/lib/api/client.ts จุดเดียว มันแนบ bearer token ให้เอง แปลง error ของ NestJS เป็นข้อความที่ UI แสดงได้ และตั้ง cache: "no-store" เพราะไม่มีอะไรใน API นี้ที่ cache ตาม URL ได้

2 · session cookie ↔ bearer token

NextAuth ถือ session ของเบราว์เซอร์ (cookie httpOnly) ส่วน apps/api เป็นเจ้าของ token จริง ไม่มีการเก็บ token ใน localStorage เลย · access token หมดอายุ apiFetch จะอ่าน session ใหม่แล้วลองซ้ำครั้งเดียว

3 · Socket.IO 2 namespace

/auctions = ห้องประมูล เปิดให้อ่านสาธารณะ ไม่ต้องมี token · /user = ของส่วนตัวรายคน ต้องพิสูจน์ตัวตนตั้งแต่ตอนเชื่อมต่อ ไม่งั้นถูกตัดทันที

4 · Prisma schema ชุดเดียว

apps/api/prisma/schema.prisma เป็นแหล่งความจริงเดียวของโครงสร้างข้อมูล ทุกโมดูลอ่าน-เขียนผ่าน Prisma · Dev 2 เป็นเจ้าของ schema และ migration ห้ามแก้โดยไม่ถาม

จุดที่คนใหม่สับสนบ่อยที่สุด

โฟลเดอร์ apps/web/src/app/api/ ไม่ใช่ API ของระบบ — มันคือ route handler ของ Next.js ที่มีไว้เพื่อจับ cookie เท่านั้น (แลก token กับ LINE, เก็บ pending token ของ OAuth, เก็บ trusted-device token) กติกาธุรกิจทั้งหมดอยู่ใน apps/api ที่พอร์ต 4000 เสมอ

วิธีอ่านตารางในบทนี้

แต่ละแถวคือหนึ่งเส้นทาง อ่านจากซ้ายไปขวาว่า หน้าจอไหน → ยิง endpoint อะไร → ข้อมูลลงตารางไหน เส้นทางที่ไม่มีคนกดแต่ระบบทำเอง จะทำเครื่องหมาย ระบบทำเอง ไว้

สิ่งที่เกิดขึ้นจริงตอนกดจ่ายเงิน

  1. ตั้งราคาใหม่ทั้งหมดที่เซิร์ฟเวอร์ — ไม่เชื่อตัวเลขที่ส่งมาจากเบราว์เซอร์แม้แต่ค่าเดียว
  2. เช็คว่าของยังขายอยู่และสต็อกพอ — ไม่พอ ตอบกลับพร้อม error code (ITEMS_UNAVAILABLE) โดยยังไม่ตัดเงิน
  3. เรียก payment provider จำลอง — ยอด 666.00 พอดีจะถูกปฏิเสธเสมอ (PAYMENT_DECLINED)
  4. ตัดสต็อกแบบมีเงื่อนไข stockQty >= quantity — ถ้าสองคนจ่ายพร้อมกัน คนที่แพ้จะ rollback ทั้งก้อน ขายเกินสต็อกไม่ได้
  5. เขียนออเดอร์แยกตามผู้ขาย + สร้าง shipment + ล้างของออกจากตะกร้า
  6. แจ้งเตือนผู้ซื้อและผู้ขายทุกคนในรอบนั้น (NOT-005) และ push ผ่าน socket /user

ต่อรองราคาตัดสินยังไง

ผู้ขายตั้ง พื้นราคา (floor) ที่ยอมรับได้ไว้ ซึ่ง ผู้ซื้อไม่มีวันเห็น — การเปรียบเทียบเกิดบนเซิร์ฟเวอร์เท่านั้น แล้วตอบกลับหนึ่งใน 3 อย่าง:

  • ACCEPTED — ข้อเสนอ ≥ ราคาที่ตั้งขายอยู่ หรือ ≥ ราคาที่ระบบ counter ไว้รอบก่อน
  • COUNTERED — ข้อเสนออยู่ระหว่างพื้นราคากับราคาขาย ระบบเสนอกลับที่ค่าเฉลี่ยของสองตัวนั้น
  • REJECTED — ข้อเสนอต่ำกว่าพื้นราคา หรือขอจำนวนเกินสต็อก

เงื่อนไขข้อแรกที่ตัวหนาคือสิ่งที่ทำให้การต่อรอง จบได้ — counter คือค่าเฉลี่ยระหว่างข้อเสนอกับราคาป้าย จึงต่ำกว่าราคาป้ายเสมอ ถ้าไม่นับ counter ของตัวเอง การเสนอเท่า counter จะได้ counter รอบใหม่ไปเรื่อยๆ เข้าใกล้ราคาป้ายแต่ไม่มีวันถึง · การกดยอมรับ counter ไม่ติดคูลดาวน์ 5 นาที เพราะตัวเลขนั้นมาจากเซิร์ฟเวอร์เอง ส่งกลับไปจึงไม่ได้เปิดเผยอะไรเกี่ยวกับพื้นราคา · ด่านเช็คพื้นราคายังอยู่เหนือทุกข้อเสมอ

ต่อรองสำเร็จแล้วไปต่อยังไง

ACCEPTED ปลดล็อกราคานั้นไว้ 15 นาที ใช้ได้ครั้งเดียว ผูกกับผู้ซื้อ สินค้า และจำนวนที่เสนอ — แต่ยังต้อง checkout ให้เสร็จเอง ต่อรองสำเร็จไม่เท่ากับซื้อสำเร็จ

ระหว่าง 15 นาทีนั้น GET /offers/pending จะคืนรายการที่ยังจ่ายได้ (พร้อม token ที่เซ็นใหม่ทุกครั้งที่อ่าน) และ PayableOffersBanner เอาไปแสดงบนหน้าสินค้า ตะกร้า checkout และรายการสั่งซื้อ — ออกจากหน้าไปแล้วกลับมาจ่ายได้ ไม่ต้องต่อรองใหม่ · ตัวกรองคือ expiresAt > now บรรทัดเดียว เพราะการใช้ token คือการดัน expiresAt ไปอดีต เงื่อนไขเดียวจึงตัดทั้ง “หมดอายุ” และ “จ่ายไปแล้ว” ออกพร้อมกัน

เส้นที่ 1 · ประมูลจนได้ของ

  5. ระบบปิดและตัดสิน ไม่มีคนกด

บทที่ 06การเทส

บทนี้แยกเป็นสองเรื่องที่ตัดสินคนละจังหวะ — เลือกเครื่องมือให้ถูก ตัดสินตอนกำลังจะเขียนไฟล์เทสใหม่ ส่วน รันให้ครบชั้น ตัดสินตอนกำลังจะส่งงาน

เลือกเครื่องมือไหน — ตัดสินจากสองคำถาม

โปรเจกต์นี้มีเครื่องมือเทส 4 ตัว และมัน ไม่ได้แข่งกัน — แต่ละตัวมีที่ของตัวเอง เวลาจะเขียนไฟล์เทสใหม่ ถามสองข้อนี้ตามลำดับ แล้วคำตอบจะออกมาเอง ไม่ต้องเถียงกันเรื่องความชอบ

ข้อ 1 · ไฟล์นี้อยู่แอปไหน → ได้ ตัวรัน

อยู่ใน apps/web = Vitest · อยู่ใน apps/api = Jest — ข้อนี้ไม่ใช่เรื่องรสนิยม แต่ละแอปตั้ง config ไว้คนละตัวอยู่แล้ว เลือกผิด = ไฟล์ไม่ถูกรันเลย

ข้อ 2 · กำลังเทสอะไร → ได้ library ที่วางทับ

ฟังก์ชันล้วน = ไม่ต้องเพิ่มอะไร · component ที่ผู้ใช้กดหรือกรอก = RTL · endpoint จริงผ่าน HTTP = Supertest

จุดที่คนมักเข้าใจผิด

RTL ไม่ใช่ทางเลือกแทน Vitest และ Supertest ไม่ใช่ทางเลือกแทน Jest — ทั้งคู่เป็นของที่ใช้ ร่วมกับ ตัวรัน ไม่ใช่แทนที่ · เทียบง่ายๆ: ตัวรันคือคนที่สั่งให้เทสเริ่มทำงานและบอกว่าผ่านหรือไม่ผ่าน ส่วน RTL กับ Supertest คือเครื่องมือที่ใช้ เอื้อมไปแตะ สิ่งที่กำลังเทส

สิ่งที่จะเทสตัวรันlibraryไฟล์ไปไว้ที่
ฟังก์ชันล้วนฝั่งเว็บ — จัดรูปแบบราคา คำนวณเวลาที่เหลือ กรองรายการ Vitest — apps/web/src/lib/<ชื่อ>.test.ts
Component ที่ผู้ใช้กด กรอก หรือเห็นข้อความเปลี่ยน Vitest RTL apps/web/src/components/<โมดูล>/<ชื่อ>.test.tsx
กติกาฝั่งเซิร์ฟเวอร์ — service, mapper, util ที่ไม่แตะฐานข้อมูลจริง Jest — (mock Prisma) apps/api/src/<โมดูล>/<ชื่อ>.spec.ts
endpoint จริง ยิงผ่าน HTTP เข้าฐานข้อมูลจริง Jest Supertest apps/api/test/<ชื่อ>.e2e-spec.ts

ทำไมสองแอปใช้ตัวรันคนละตัว

apps/api → Jest

มากับ nest new ตั้งแต่วัน scaffold และ e2e ใช้ Test.createTestingModule() ของ NestJS ซึ่งผูกกับระบบ DI ของ Nest — ย้ายไปตัวอื่นแปลว่าต้องรื้อวิธีประกอบโมดูลใหม่ทั้งหมด โดยไม่ได้อะไรกลับมา

apps/web → Vitest

Next.js 16 เป็น ESM ล้วนและใช้ alias @/* · Vitest อ่าน path จาก tsconfig.json ให้เลยผ่าน resolve.tsconfigPaths — path ที่ resolve ได้ในเอดิเตอร์จึง resolve ได้ในเทส โดยไม่ต้องประกาศซ้ำในไฟล์ config

อย่าสลับกัน

อย่าลาก Vitest เข้า apps/api หรือลาก Jest เข้า apps/web เพราะถนัดตัวไหน — แอปเดียวมีสองตัวรันแปลว่าคนที่เปิดไฟล์มาเดาไม่ออกว่าไฟล์นี้รันด้วยอะไร และ pnpm test ที่รากจะรันไม่ครบโดยไม่มีใครรู้ตัว

RTL — เทสสิ่งที่ผู้ใช้เห็น ไม่ใช่สิ่งที่โค้ดทำข้างใน

  • หาอิลิเมนต์ด้วยสิ่งที่ผู้ใช้ใช้หา — getByRole("button", { name: "บิด" }) หรือ getByLabelText ไม่ใช่ class หรือ test id · ถ้าหาด้วย role ไม่เจอ มักแปลว่า คนที่ใช้ screen reader ก็หาไม่เจอเหมือนกัน — นั่นคือบั๊กจริง ไม่ใช่ปัญหาของเทส
  • ใช้ user-event ไม่ใช่ fireEvent — user-event จำลองลำดับที่เบราว์เซอร์ทำจริง (focus → keydown → input → change) ส่วน fireEvent ยิง event เดี่ยวๆ ซึ่งผ่านได้ทั้งที่ของจริงพัง
  • ไม่ต้องเรียก cleanup เอง — apps/web/src/test/setup.ts ตั้ง afterEach(cleanup) ไว้แล้ว ถ้าไม่มี component จากเทสก่อนหน้าจะค้างใน DOM แล้ว getByRole จะเจอสองตัวและ throw

Supertest — ยิงเข้าแอปที่ประกอบเหมือน production

บรรทัดที่ลืมแล้วเทสจะโกหก

ทุกไฟล์ e2e ต้องเรียก configureApp(app) ต่อจาก createTestingModule — ValidationPipe และ exception filter ถูกติดตั้งใน main.ts ไม่ใช่ใน AppModule ไฟล์ที่ลืมบรรทัดนี้จะรันแอปที่ไม่มีการตรวจ input เลย เทสเขียวสวยแต่ของจริงรับค่าอะไรก็ได้

ของที่ไม่ต้องเขียนเทส

เทสที่ไม่ได้ปกป้องอะไรมีต้นทุนจริง เพราะต้องตามแก้ทุกครั้งที่โค้ดขยับ · สามอย่างนี้ปล่อยผ่านได้: ค่าคงที่และ type (typecheck จับให้แล้ว) · Prisma ทำงานถูกไหม (นั่นคือเทส library ของเขา ไม่ใช่โค้ดเรา) · component ที่ render ข้อความตายตัวโดยไม่มีเงื่อนไข · ที่คุ้มที่สุดคือจุดที่มี เงื่อนไขหรือการคำนวณ — บิดขั้นต่ำ การตัดสินกันยิงท้าย การตัดสต็อก

เลือกวิธีไหน — เทสที่ชั้นไหนถึงคุ้ม

เลือกเครื่องมือถูกแล้วยังเหลืออีกคำถามที่สำคัญกว่า: เรื่องนี้ควรเทสที่ชั้นไหน · มีหลักเดียวพอ — เทสที่ชั้นต่ำที่สุดที่ยังพิสูจน์สิ่งที่กลัวได้จริง

วิธีใช้หลักนี้คือถามตัวเองว่า "ถ้าของชิ้นนี้พัง มันพังที่ไหน" แล้วเทสตรงนั้น — ไม่ใช่ไล่ขึ้นไปเทสที่ชั้นบนสุดเพราะรู้สึกว่าจริงกว่า ชั้นบนช้ากว่ามากและพังบ่อยกว่าด้วยเหตุผลที่ไม่เกี่ยวกับโค้ดเรา

สิ่งที่กลัวว่าจะพังเทสที่ชั้นทำไมชั้นอื่นจับไม่ได้
คำนวณผิด — บิดขั้นต่ำ ส่วนลดตามจำนวน เวลาที่เหลือ ค่าเฉลี่ยที่ AI counter unit e2e จับได้เหมือนกันแต่ช้ากว่ามาก และเวลาแดงจะไม่บอกว่าผิดที่บรรทัดไหน
ปุ่มเปิด/ปิดผิดจังหวะ · ข้อความ error ไม่ขึ้น · กรอกแล้วหน้าจอไม่ตอบสนอง component (RTL) typecheck กับ next build จับได้แค่ว่า render ผ่าน ไม่ได้จับว่ากดแล้วเกิดอะไร
migration apply ไม่ผ่าน · unique index ชน · สองคนกดพร้อมกันแล้วสต็อกติดลบ · guard ต่อผิดลำดับ e2e เท่านั้น unit จับไม่ได้เลย เพราะ mock Prisma ทิ้งไปหมดแล้ว — ของพวกนี้เป็นพฤติกรรมของฐานข้อมูลจริง
หน้าเว็บพังตอน build · Server Component เรียกของที่เรียกไม่ได้ ไม่ต้องเขียนเทส next build ใน CI จับให้แล้ว — เขียนเทสซ้ำคือจ่ายฟรี
เส้นทางที่พาดหลายหน้า — ประมูลจบ → ไป checkout → ได้ออเดอร์ ยังต้องกดมือ e2e ครอบเฉพาะฝั่ง API · ยังไม่มีเทสที่ขับเบราว์เซอร์จริงในโปรเจกต์นี้
กฎกันเทสเฟ้อ

WebSocket — ทำไมประมูลถึงต้องมี

คำถามที่ต้องตอบให้ได้ก่อนคือ REST อย่างเดียวไม่พอตรงไหน · คำตอบอยู่ที่ลักษณะของข้อมูล: ราคาประมูลเปลี่ยนเพราะ คนอื่น ไม่ใช่เพราะคนที่กำลังดู — REST ตอบได้เฉพาะตอนที่มีคนถาม ส่วนคนดูประมูลไม่มีทางรู้ว่าควรถามเมื่อไหร่

ทางเลือกผลที่ได้จริง
กด refresh เอง ผู้ใช้ต้องเดาเองว่าตอนไหนราคาขยับ — ในห้องประมูลนาทีสุดท้ายคือใช้ไม่ได้เลย
polling ทุก 1–2 วิ ผู้ชม 1 คน = คำขอเปล่าหลายสิบครั้งต่อนาที และ ยังช้ากว่าอยู่ดี เพราะข่าวมาถึงช้าสุดเท่ากับ 1 รอบ polling — จ่ายแพงกว่าเพื่อได้ของที่แย่กว่า
WebSocket เซิร์ฟเวอร์บอกตอนที่มีอะไรเกิดขึ้นจริง ไม่มีคำขอเปล่า และถึงทันที

เกณฑ์ที่ใช้ตัดสินคือ ข้อมูลถูกผลักโดยเหตุการณ์ที่คนดูไม่ได้ก่อหรือเปล่า — ประมูล แจ้งเตือน และแชทเข้าเกณฑ์นี้ · ส่วนตะกร้าหรือหน้าโปรไฟล์ไม่เข้า เพราะมันเปลี่ยนก็ต่อเมื่อเจ้าของกดเอง จึงไม่ได้เอา socket ไปแปะทุกหน้า

ทำไม Socket.IO ไม่ใช่ WebSocket ดิบ

ของ 4 อย่างนี้ต้องมีอยู่แล้ว ถ้าใช้ WS ดิบก็ต้องเขียนเองทั้งหมด

ห้อง (rooms)

ต้องยิงเข้าเฉพาะคนที่ดูประมูลนั้น ไม่ใช่ทุกคนที่ต่ออยู่ · WS ดิบต้องทำ registry ของ connection เอง

ต่อใหม่อัตโนมัติ

เน็ตสะดุดกลางประมูลคือจังหวะที่แย่ที่สุด · use-auction-room.ts ตั้ง backoff 1 วิ → สูงสุด 10 วิ ให้เอง

namespace

แยกช่องสาธารณะกับช่องส่วนตัวออกจากกันได้โดยไม่ต้องเปิดพอร์ตเพิ่มหรือทำ handshake เอง

fallback

เครือข่ายที่บล็อก WebSocket จะถอยไป long-polling เองโดยโค้ดฝั่งเราไม่ต้องรู้เรื่อง

บวกกับที่ NestJS มี @nestjs/platform-socket.io ให้ในตัว — gateway เขียนเป็นคลาสที่ใช้ DI ชุดเดียวกับ service อื่น เข้าถึง PrismaService ได้เหมือนกัน ไม่ต้องต่อสายเอง

ทำไมแยกเป็น 2 namespace

เพราะทั้งสองช่องมี คุณสมบัติด้านความปลอดภัยตรงข้ามกัน — เอามารวมกันแปลว่าต้องกรองรายคนในห้องเดียว ซึ่งพลาดครั้งเดียวคือข้อมูลรั่ว

/auctions/user
ใครเข้าได้ ไม่ต้องมี token ต้องพิสูจน์ตัวตนตอนเชื่อมต่อ
เพราะอะไร ประมูลที่เผยแพร่แล้วเป็นข้อมูลสาธารณะ (AUC-005) และห้องส่งข้อมูลชุดเดียวกับที่ GET สาธารณะส่งอยู่แล้ว — ไม่มีอะไรให้อนุญาต ทุก event จ่าหน้าถึงบัญชีเดียว socket ที่พิสูจน์ตัวเองไม่ได้จึงไม่มีเหตุผลจะต่ออยู่
ส่ง token มาด้วยได้ไหม ได้ และไม่เปลี่ยนสิ่งที่เห็น — มีไว้ให้ระบบรู้ว่าใครปิดแท็บ ตัวนับผู้ชมจะได้ถูก (LIV-001) บังคับ
รายละเอียดที่ตั้งใจทำแบบนี้

/user ตรวจตัวตน ตอนเชื่อมต่อ ไม่ใช่ตอนส่งข้อความ join — จึงไม่มีช่วงเวลาไหนเลยที่ socket ซึ่งยังไม่รู้ว่าเป็นใครเกาะอยู่กับ namespace นี้เพื่อรอบอกว่าตัวเองคือใคร

หลักที่สำคัญที่สุด — socket บอกว่า "มีอะไรเปลี่ยน" ไม่ได้บอกว่า "เปลี่ยนเป็นอะไร"

ทุก handler ใน use-auction-room.ts เรียก onChange() เหมือนกันหมด แล้วหน้าจอไปยิง GET /arena อ่านใหม่ทั้งชุด — ไม่มีที่ไหนเอา payload ของ event มาแปะหน้าจอตรงๆ

เหตุผล: arena เป็นค่าชุดที่ ต้องสอดคล้องกันทั้งก้อน — ราคาปัจจุบัน ผู้นำ บิดขั้นต่ำถัดไป เวลาปิด และโควตาต่อเวลาที่เหลือ · API คำนวณมันมาพร้อมกัน การหยิบมาแปะทีละฟิลด์คือวิธีที่ทำให้หน้าจอ เสนอบิดที่ endpoint จะปฏิเสธ · ต้นทุนคือ 1 request ต่อ 1 event ได้กลับมาคือสถานะที่ถูกทั้งก้อนเสมอ

socket ไม่รับคำสั่ง

การบิดยังต้องผ่าน HTTP และ guard ตามปกติ — socket รับแค่ข้อความ join ห้อง นอกนั้นเป็นทางเดียว (ออกอย่างเดียว) ผลที่ได้คือ ไม่มีกติกาธุรกิจข้อไหนที่ต้องเขียนสองที่ ถ้ารับบิดผ่าน socket ด้วย ทุกกฎ (บิดขั้นต่ำ กันบิดซ้ำ สิทธิ์ผู้ใช้) จะต้องมีสำเนาที่สอง และสองสำเนาย่อมหลุดจากกันสักวัน

presence เก็บใน memory โดยตั้งใจ

presence-registry.ts เก็บว่า socket ไหนเป็นของใครและกำลังดูประมูลอะไร ไว้ในหน่วยความจำล้วน เหตุผลคือมันอธิบายว่าใครต่ออยู่กับ process นี้ — process ตายเมื่อไหร่ socket ที่มันถืออยู่ก็หายไปด้วย ข้อมูลจึงถูกต้องโดยธรรมชาติ ไม่ต้องมีใครมาล้างให้

และมัน นับ ไม่ใช่ติดธง เพราะคนเดียวเปิดประมูลเดียวกันได้สองแท็บ — ปิดไปแท็บหนึ่งไม่ได้แปลว่าออกจากห้อง

ข้อจำกัดที่ต้องรู้ก่อนขยาย

ทั้ง presence และการ broadcast ผูกกับ process เดียว · วันที่รัน apps/api มากกว่า 1 instance ต้องเพิ่ม Socket.IO adapter (เช่น Redis) ก่อน ไม่งั้นคนที่ต่ออยู่คนละ instance จะไม่เห็น event ของกันและกัน และตัวนับผู้ชมจะนับได้แค่คนที่บังเอิญมาต่อ instance เดียวกัน · ตอนนี้ยังไม่มี adapter ในโค้ด (ค้นทั้ง apps/api/src ไม่เจอทั้ง Redis และ IoAdapter) — ออกแบบไว้สำหรับ instance เดียว และนี่คือสิ่งแรกที่ต้องแก้ก่อนเพิ่มจำนวน instance จำนวน replica จริงตั้งอยู่ใน dashboard ของ Railway ไม่ได้อยู่ในรีโป จึงต้องไปดูที่นั่นก่อนสรุปว่าตอนนี้รันกี่ตัว

  1. prisma migrate deploy ก่อน start

    ฐานข้อมูลที่ container เพิ่ง start มาเจอ มักตามหลังโค้ดอยู่หลาย migration — นั่นคือสภาพปกติหลัง deploy · migrate deploy apply เฉพาะที่ขาด ไม่เขียนประวัติใหม่ และ จับ advisory lock ก่อน สอง container ที่ start พร้อมกันจึงแย่ง migration เดียวกันไม่ได้

  2. exec node ไม่ใช่เรียกเฉยๆ

    exec ทำให้แอปแทนที่ shell แล้วกลายเป็น PID 1 — รับ SIGTERM จากแพลตฟอร์มตรงๆ · ถ้าไม่ใช้ shell จะกลืนสัญญาณไว้ graceful shutdown ไม่ทำงาน แล้ว container โดน kill ทิ้ง ทั้งที่ยังมี request ค้างอยู่

ปล่อยงานทีละขั้น

  1. เช็คว่ามีอะไรค้างรอปล่อยบ้าง

    อ่านอย่างเดียว ไม่ได้สร้าง PR รันกี่รอบก็ได้
    git fetch origin
git log --merges --pretty='- %s' origin/main..origin/dev

    ไม่มีอะไรขึ้นเลย = main ตามทัน dev แล้ว รอบนี้ไม่ต้องปล่อย

  2. เปิด release PR — base ต้องเป็น main

    เปิดหน้า compare main...dev ตรวจว่าหัวเพจเป็น base: main ← compare: dev และขึ้นว่า Able to merge · title ใช้รูปแบบ chore: release dev to main - <สรุปสั้นๆ> · description สั้น 2–3 บรรทัด อ้างเลข PR ลูกพอ (พิมพ์ #153 เฉยๆ GitHub ทำลิงก์ให้เอง)

    นี่เป็น PR ชนิดเดียวที่ base เป็น main ได้ feature branch ต้องเข้า dev เสมอ

  3. กด Update branch ทันที อย่ารอ CI

    ถ้ารอ CI จบก่อนแล้วค่อยกด Update จะเสียเวลาฟรีหนึ่งรอบเต็ม เพราะ commit ที่กำลังเทสไม่ใช่ commit ที่จะ merge จริง · ห้ามเลือก Update with rebase เพราะจะเขียนประวัติ dev ใหม่ทั้งเส้น

  4. รอ CI ครบ 3 เขียว แล้วขอ approve 1 คน

    branch protection บังคับ lint-and-test + docker-build + e2e และต้องมีคน approve 1 คน — กด merge เองคนเดียวไม่ได้

  5. กด Merge แล้ว Railway กับ Vercel deploy เอง อัตโนมัติ

    docker-entrypoint.sh รัน prisma migrate deploy ให้เองก่อน start ทุกครั้ง ตอน deploy จึงไม่ต้องรัน migration แยก

  6. ตรวจว่า production ยังหายใจอยู่

    Git Bash — เปลี่ยน <railway-domain> เป็นโดเมนจริง
    curl https://<railway-domain>/health
    PowerShell — curl ที่นี่เป็น alias ของ Invoke-WebRequest ไม่ใช่ curl ตัวจริง
    Invoke-RestMethod https://<railway-domain>/health

    ต้องได้ {"status":"ok"} เป๊ะแบบนี้เท่านั้น — ได้อย่างอื่นแปลว่ายิงผิดเซิร์ฟเวอร์ เพราะโดเมน Railway เป็นชื่อสาธารณะที่ใครก็จองได้ ยิงผิดตัวก็ได้ 200 กลับมาเหมือนกัน ปิดท้ายด้วยการลองกดใช้ฟีเจอร์ที่เพิ่งปล่อยบนเว็บจริงสัก 1 อย่าง
